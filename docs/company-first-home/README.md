# Company-first sign-in

The account home is a directory, not an active reporting workspace. Normal sign-in always displays saved companies/periods, including a one-company account. Existing explicit service intents retain their validated routing. A company name or Open workspace action opens that exact company/year with `?view=company`; the query is presentation-only and grants no access or service scope.

The directory omits the account workflow sidebar, duplicate upload entry and standalone Continue panel. Setup drafts remain visible and selectable. The selected workspace shows company details, its existing server-derived next action and the same released, access-filtered tasks as its rail. Financial Statements, Close Review and Sign-off are offered only where existing reporting enablement permits them. No speculative future features are advertised. Legacy direct task URLs retain their behaviour.

Period rows remain separate: grouping a truncated server page into apparently complete company groups would conceal years. Pagination, search, filters, exact totals and change-token protection use the existing portfolio contract. The bounded draft sample keeps its existing explicit overflow link to company management; this change does not introduce an unbounded read or a new directory API. Saved setup drafts are database company records; a browser-only edit is not represented as a saved company.

A company with no engagement still requires an explicit service start using the existing idempotent command. Merely opening the menu creates nothing. Plan/capacity discovery, archive access, permissions, purchased scope, financial validation, accepted currency locks, request identities and audit records remain authoritative. Civil reporting dates display in UTC so a browser timezone cannot shift the recorded calendar date.

Verification covers ordinary single-company sign-in, saved drafts, read failure/retry, expired-plan archive access, explicit year destinations, released versus withheld task menus, and the existing upload/setup/recovery journey on desktop and mobile. Failure injection uses the isolated development transport; actual backend acceptance belongs to CI's real-stack and disposable-database jobs. No production data, payments, merge or publishing is part of this work.
