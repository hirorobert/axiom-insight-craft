# Ω3-CHECKOUT — Implementation Plan

Design document only. Nothing below has been applied. Every file is marked MUST CHANGE / MAY CHANGE / MUST NOT CHANGE for a future, separate implementation pass — subject to the independent Codex audit this package exists to enable.

**Design-correction round 1:** the resolver deployment is now explicitly three-phase (schema → application → cleanup), `commit_verified_commercial_payment` moves from MUST NOT CHANGE to MUST CHANGE (a customer-level lock is required — item 6), `admin_upsert_commercial_offer` gains the same product-scoping fix as the resolver, the two USD offers are seeded non-purchasable with a separate activation step (item 12), `list_purchasable_commercial_offers` is withdrawn entirely (item 9 — no proven caller), and every "renewal" reference means manual, customer-initiated renewal (item 8).

**Design-correction round 2:** round 1's `resolve_commercial_offer` product-scoping relied on `auth.uid()`, which is `NULL` under the service-role client `commercial-create-checkout` actually uses — split into `resolve_commercial_offer` (display) and a new, service-role-only `resolve_commercial_checkout_offer` (checkout, item 1). The single-RPC `acquire_or_reuse_checkout_intent` from round 1 is withdrawn and replaced by a three-RPC, token-fenced lease protocol (item 3). `admin_supersede_commercial_offer` cannot activate/deactivate an existing offer row in place — a new, narrow `admin_set_offer_purchasable` RPC is added (item 4). `admin_upsert_commercial_offer` gains an explicit product-code parameter (item 5). The webhook `chk_pwpe_result` CHECK constraint gets exact DDL for one new value (item 6). Reconciliation is committed to one mechanism (item 7). The platform-state gate is corrected (item 8). GLOBAL-only checkout's effect on Tanzania offers is stated explicitly (item 9). Every new function's exact privilege grant is specified (item 2).

**Design-correction round 3:** round 2's lease RPC was checked against the real `payment_checkout_intents` schema and found unexecutable — a nonexistent `checkout_url` column and four omitted `NOT NULL` columns. Corrected, with economics now derived from the locked offer row rather than passed loose (item 1). Exact `chk_pci_status`/`idx_pci_status_active` DDL is added for the new `PROVIDER_CREATING` status (item 3). Reconciliation outcomes move to a NEW dedicated `payment_reconciliation_attempts` table (item 4). The reconciliation claim becomes a durable, token-fenced lease (item 5). Backoff arithmetic and the exact maximum elapsed window are stated (item 6). Cron authentication moves from an unusable placeholder to a Vault-backed secret (item 7). The `LEASE_HELD` response becomes a bounded 202/`Retry-After` contract (item 8). The platform-state gate's fail-open gap is closed (item 9). `admin_supersede_commercial_offer`'s defect is fixed (item 10). Flutterwave's lookup-by-reference gets a full specification (item 11). A required executable migration-replay acceptance gate is added (item 12).

**Design-correction round 4:** a fourth review found round 3's own reconciliation claim/terminal predicates both required `expires_at > now()` — but `expires_at` is 1 hour and the reconciliation programme runs up to 305 minutes, so any intent past its 1-hour checkout-session expiry would be silently stranded, unreachable by either the claim or the terminal-transition logic. `DATA_CONTRACTS.md` §7.0 (new) states one canonical rule fully decoupling checkout-session expiry from reconciliation eligibility, and corrects `authoriseCommit` plus `commit_verified_commercial_payment` to compare the provider's own payment timestamp against `expires_at`, never wall-clock now() (item 3). `provider_environment` is added to `payment_checkout_intents`, snapshotted at acquisition, required to match on reuse (item 1). `acquire_checkout_intent_lease` now locks the offer row `FOR SHARE` and independently re-verifies cross-product and provider-restriction (item 2). The `CLAIMED` evidence row is now inserted atomically inside the claim RPC itself (item 4). Round 3's `release_reconciliation_lease` is replaced by `finalize_reconciliation_attempt` — the sole, token-CAS'd, never-overwrites-`SUCCEEDED` path for recording any attempt's outcome, including cap-exhaustion (item 5). The backoff anchor becomes the real `reconciliation_last_completed_at`, not a lease-start approximation (item 6). The cron job's project-URL source is now explicitly provisioned via `ALTER DATABASE`, secret installation is fully specified, and a SHA-256 fingerprint preflight blocks cron activation on any Vault/Edge-secret mismatch (item 7). Twelve new executable acceptance tests are added (item 8).

**Design-correction round 5 (this revision, surgical — modifies only the specific blocks these findings name, per the mission's own "do not broadly rewrite" instruction):** Codex's round-4 audit found round 4's own fixes still contained six BLOCKERS and two HIGH inconsistencies. **The single most important finding: round 4's own `acquire_checkout_intent_lease` staleness sweep still transitioned `PENDING` → `EXPIRED` merely because `expires_at` passed** — the exact canonical-rule violation §7.0 was written to prevent, still present, unfixed, because round 4 fixed the RECONCILIATION predicates but never went back to fix this specific `UPDATE` statement. **A second, independent occurrence of the identical defect was found in the REAL, live `commit_verified_commercial_payment` function** (`IF now() > v_intent.expires_at THEN UPDATE ... SET status='EXPIRED'`), which no round had ever actually quoted verbatim before now — every prior round described this function only in prose. Both are corrected via a new, explicit four-part lifecycle model (URL-reuse-freshness / payment-resolution-status / reconciliation-status / manual-review-status, a new `requires_manual_review` column) — Blocker 1. The prose-only "crashed-terminal-attempt sweep" is replaced with complete, executable SQL — Blocker 2. Every `billing_audit_events` insert this design proposed omitted the real table's `NOT NULL billing_customer_id` column and would have failed outright — corrected against the real schema, `correlation_id` typed `UUID` throughout, never TEXT — Blocker 3. The claim RPC's `SELECT c.*, c.reconciliation_claim_token` did not produce the declared two-column composite return shape — corrected to an explicit whole-row cast, with the exact TypeScript decoding shape shown — Blocker 4. The claimed "select the adapter matching the intent's environment" had only one adapter instance to select from — a genuine dual-environment credential architecture (separate sandbox/production secrets, environment-parameterized adapter construction, routing-based webhook environment selection) is specified in full — Blocker 5. `ALTER DATABASE ... SET app.settings.project_url = '<project-ref>...'` inside a migration that runs identically in every environment is removed — the URL is now Vault-provisioned per environment, exactly like the cron secret, with an explicit validation function proving HTTPS/hostname/project-ref/no-path-injection and blocking cross-environment targeting — Blocker 6. Flutterwave's `data.created_at` is no longer asserted as proven payment-completion semantics without qualification — the exact citation, its limits, and fail-closed handling for missing/malformed/impossible values are specified, and the real, already-existing `payment_events.provider_created_at` column (never previously identified) is correctly populated instead of a hardcoded `now()` — High 1. The retry-count contract (`maxAttempts=3` = 1 initial + 2 retries, never a "4th observed response") is unified across every document, with full `Retry-After` sanitization and a deadline enforced before every request, not merely once — High 2A. Every acceptance-test expectation that a crashed terminal attempt transitions to `FAILED` via "a terminal CTE" is removed and replaced with the one canonical outcome (`requires_manual_review = true`, status unchanged) — High 2B.

**Design-correction round 6 (this revision, surgical):** a sixth review found that round 5's OWN fix for `commit_verified_commercial_payment` repeated the identical overload-discipline mistake round 5 corrected for every other function in this package — its `CREATE OR REPLACE FUNCTION` call adding `p_provider_created_at` does not replace the vulnerable 12-arg signature at all, it creates a second, co-existing 13-arg overload, leaving the OLD, wall-clock-vulnerable function fully callable. Corrected into the same three-phase (Phase A create / Phase B cut over / Phase C `REVOKE`+`DROP` old signature) discipline used everywhere else, with an executable `pg_proc` query proving the 12-arg signature is gone and a required `PGRST202` failure on any direct 12-arg RPC call — item 1. `requires_manual_review = true` rows were never excluded from the automatic reconciliation claim or crash-reclaim predicates — both now exclude them unconditionally, with a new audited, `is_commercial_admin()`-gated `admin_reopen_reconciliation` RPC as the sole re-entry path — item 2. The webhook path had no mechanism to record its own discovery of `PAYMENT_AFTER_INTENT_EXPIRY` or an environment mismatch — it has no reconciliation claim token and must never fabricate one to call `finalize_reconciliation_attempt` — closed with a new, narrow, claim-token-free `flag_webhook_payment_requires_manual_review` RPC, service-role-only — item 3. Round 5's single-function `WEBHOOK_ENVIRONMENT` env-var design assumed an unsupported Supabase deployment capability (one source deployed twice under different config) — replaced with two genuinely separate, source-controlled Edge Function directories (`commercial-payment-webhook-sandbox`, `commercial-payment-webhook-production`), each hardcoding its environment identity as a literal and calling one shared handler — item 4. A new check compares the loaded intent's own `provider_environment` against the authenticated webhook route's hardcoded environment BEFORE Gate B or commit, closing a cross-environment corroboration gap Gate A alone does not close — item 5. Flutterwave's `data.created_at` semantics move from a qualified caveat to a named, tracked, explicitly BLOCKING pre-implementation gate (`GATE-FLUTTERWAVE-CREATED-AT-SEMANTICS`) with exact numbered closure criteria — item 6. Executable Postgres/Edge test requirements for all six corrections are added to `ACCEPTANCE_MATRIX.md` — item 7. All six documents are swept for contradictory legacy text — item 8. Full design: `DATA_CONTRACTS.md` §7.0, §7.2, §7.4, §12.4.

## 2. Concurrency implementation note

The token-fenced lease protocol (`acquire_checkout_intent_lease` / `persist_checkout_provider_result` / `fail_checkout_intent_lease`, `DATA_CONTRACTS.md` §3) and the customer-level lock inside `commit_verified_commercial_payment` (`DATA_CONTRACTS.md` §11, unchanged since round 1) are both **database-enforced**, not application-level check-then-act logic. The lease protocol itself superseded an intermediate, single-RPC atomic design from round 1 that was correctly atomic for its own transaction but left an unlocked window during the external provider call — see `COMMERCIAL_ARCHITECTURE_AUDIT.md` §6 for why that intermediate design was still insufficient. See `THREAT_AND_FAILURE_MODEL.md` Part 1 for the full scenario-by-scenario re-audit across both rounds.

## 3. Migration safety

- **Phase A migration** (all new functions and schema additions listed in §1's MUST CHANGE table above — the 3-arg `resolve_commercial_offer`, `resolve_commercial_checkout_offer`, the three lease RPCs, `admin_set_offer_purchasable`, the `admin_upsert_commercial_offer` 12-arg overload, the `chk_pwpe_result` DDL, the reconciliation schema and RPC, the new 13-arg `commit_verified_commercial_payment` overload, `admin_reopen_reconciliation`, `flag_webhook_payment_requires_manual_review`): forward-only, no `DROP TABLE`, no destructive alteration. Both old overloads (`resolve_commercial_offer(TEXT,TEXT)`, `admin_upsert_commercial_offer`'s 11-arg form) AND the old 12-arg `commit_verified_commercial_payment` signature are left in place and functioning exactly as before for the duration of this phase — this migration changes zero existing behavior for any in-flight caller (**corrected round 6, item 1** — round 5 believed its `commit_verified_commercial_payment` change belonged in this "zero behavior change" category by construction; it does, but only once correctly understood as a new-overload addition rather than a same-signature replace).
- **Phase B** (application deploy): the Edge Function and frontend changes — including cutting every payment-commit caller (the webhook shared handler, the reconciliation function) over to the new 13-arg `commit_verified_commercial_payment` overload — plus the new `commercial-payment-reconcile` function, the two webhook wrapper functions (`commercial-payment-webhook-sandbox`/`-production`, item 4) and their shared handler, and the `pg_cron` schedule. Rollback of this phase alone is safe — every old overload (including the 12-arg payment-commit signature) remains present and callable, so a reverted Edge Function continues to work exactly as it did before any of this shipped.
- **Phase C migration(s)** (drop the old 2-arg `resolve_commercial_offer(TEXT,TEXT)` overload, the old 11-arg `admin_upsert_commercial_offer` overload, AND — **as its own separately-gated migration, round 6, item 1** — the old 12-arg `commit_verified_commercial_payment` signature with its executable absence proof): each deployed only after its own Phase B cutover is confirmed stable — see the three-phase deployment order in `DATA_CONTRACTS.md` §1, §5, and §7.0. This is the direct answer to item 1's "define safe migration/Edge-Function deployment order" requirement, applied consistently to every function that gained a new overload rather than a same-signature replace.
- **Controlled commercial data-seed operation:** unchanged in kind from the prior round (an admin RPC call, not a migration, reversible via supersession, never a `DELETE`) — corrected only in that Step 1 (create) and Step 2 (activate) are now explicitly two separate, independently-audited operations (item 12).
- Pre-deployment verification: the full existing commercial test suite plus every new/updated test in §1's MUST CHANGE row. None of the existing tests assert a fixed resolver arity as a requirement (re-confirmed this round) except `marketPropagation.test.ts`, which is explicitly retired.
- Post-deployment verification: `ACCEPTANCE_MATRIX.md` in full, including the new platform-state, concurrency, product-binding, and manual-renewal-disclosure sections.
- Frontend economics: `Pricing.tsx`'s `PRICING.MONTHLY_USD`/`ANNUAL_USD` constants remain a **display fallback only until the resolver call succeeds** — once checkout is enabled, the page must render the server-resolved amount for the actually-selected interval (item 9), and a detected mismatch between the two must **disable the checkout CTA and raise an acceptance failure**, not merely log a warning. See §5.

## 5. Public pricing / authoritative offer drift, and the withdrawn listing function (items 9)

**Parity mechanism, corrected to be enforcing, not advisory:** `Pricing.tsx`, once wired to real checkout, must call `resolve_commercial_offer` for both intervals (or lazily for the selected one) and compare the returned `amount_minor`/`currency_code` against `PRICING.MONTHLY_USD`/`ANNUAL_USD`. On a match, render normally. **On a mismatch, disable the checkout CTA and surface a visible "pricing temporarily unavailable" state** — this is the acceptance-failure behavior item 9 requires, replacing the prior round's softer "staging smoke test / admin warning" framing, which did not actually prevent a live mismatch from reaching a customer. This still makes the DB the sole authority (the frontend never invents a number; it only refuses to proceed on disagreement) and still requires no new architecture.

**`list_purchasable_commercial_offers` is fully withdrawn** — not deferred, not "may change." If a genuine future need for an interval-independent listing surface arises (e.g. an admin catalogue UI), it gets its own design pass with a real, named caller identified first.
