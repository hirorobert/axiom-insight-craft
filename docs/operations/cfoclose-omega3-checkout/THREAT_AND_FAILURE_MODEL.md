# Ω3-CHECKOUT — Threat and Failure Model

Design/audit document. Covers concurrency (Step 6) and failure-state classification (Step 8).

**Design-correction round 1:** re-audited against the corrected atomic checkout-intent design and customer-level commit lock. Scenarios 1, 2, and 13 re-analyzed against the atomic RPC; scenario 6 given a complete design; scenario 8 given a deterministic outcome; two crash-recovery scenarios added; webhook reliability re-classified per the transient/definitive split. "Renewal" throughout means manual, customer-initiated — this design ships a prepaid term licence, never automatic recurring billing (item 8).

**Design-correction round 2:** round 1's single-RPC checkout-intent design (scenarios 1, 2, 13, 14, 15) is superseded by the token-fenced lease protocol (`DATA_CONTRACTS.md` §3) — three new scenarios (live-lease contention, stale-lease takeover, failed-CAS non-disclosure) are added, alongside reconciliation concurrency (`SKIP LOCKED`), offer-activation compare-and-swap, and the corrected provider-selection-ordered platform-state gate.

**Design-correction round 3:** the `LEASE_HELD` response contract is corrected from an unbounded 409 to a bounded, 202-with-`Retry-After` client retry protocol (item 8); the reconciliation claim mechanism is corrected from a timestamp-only claim to a durable, token-fenced lease (item 5) — scenarios 21, 22 cover crash recovery; scenario 23 covers Flutterwave's lookup-by-reference returning multiple matches (item 11); the reconciliation evidence table reference is corrected to `payment_reconciliation_attempts` (item 4).

**Design-correction round 4:** round 3's own reconciliation claim/terminal predicates required `expires_at > now()` — a genuine contradiction with the 305-minute reconciliation programme, since `expires_at` is 1 hour; any intent older than that would have been stranded, unreachable by either predicate. Scenarios 24–27 covered the corrected canonical rule.

**Design-correction round 5 (this revision):** round 4's own scenario 25 ("Unpaid intent, no webhook ever arrives") correctly described reconciliation's corrected eligibility, but round 4 never revisited `acquire_checkout_intent_lease`'s OWN staleness sweep, which still transitioned `PENDING`→`EXPIRED` on `expires_at` alone — the exact violation the canonical rule exists to prevent, confirmed still present and now fixed (Blocker 1, scenario 25's row updated below). Scenario 21's outcome is corrected from "the terminal CTE transitions the row to `FAILED`" (obsolete, never actually true even in round 3's design, and structurally impossible now that a crashed attempt has no completed provider result to classify against) to the one canonical `requires_manual_review` outcome (High 2B). Four new scenarios (28–31) cover the remaining round-5 findings: a genuinely late payment rejected without a status side effect, a `billing_audit_events` insert against the real schema, the claim RPC's corrected composite return shape, and dual-environment credential isolation at both checkout and webhook-verification time.

**Design-correction round 6 (this revision):** a sixth review found round 5's OWN `commit_verified_commercial_payment` fix repeated the identical overload-discipline defect round 5 corrected everywhere else — its `p_provider_created_at` parameter creates a co-existing 13-arg overload, leaving the old 12-arg, wall-clock-vulnerable signature fully live (item 1, scenario 32). `requires_manual_review = true` rows were never actually excluded from the claim/crash-reclaim predicates that reference the column (item 2, scenario 33). The webhook path had no way to record its own discovery of an expired or environment-mismatched payment without fabricating a reconciliation claim token it never legitimately holds (item 3, scenario 34). Round 5's single-function `WEBHOOK_ENVIRONMENT` design assumed an unsupported Supabase deployment capability (item 4, scenario 35). A loaded intent's own `provider_environment` was never cross-checked against the authenticated webhook route before commit (item 5, scenario 36). Flutterwave's `data.created_at` semantics move from a caveat to a named, tracked, blocking pre-implementation gate (item 6, scenario 37).

**Design-correction round 7 (this revision):** a seventh review found round 6's own acceptance test for scenario 33's mitigation asserted "no code path ever sets `requires_manual_review` back to `false`" — a claim round 6's OWN `admin_reopen_reconciliation` RPC (also introduced in scenario 33) directly contradicts, since clearing the flag is that RPC's entire purpose. Corrected canonical invariant: no AUTOMATIC path clears it; `admin_reopen_reconciliation` alone may, under its existing admin/reason/PENDING/flagged gates (item 1, scenario 33's row updated below). Round 6's `flag_webhook_payment_requires_manual_review` (scenario 34, 36) had no idempotency guard — a duplicate or concurrent webhook delivery reaching an already-flagged intent would insert a second, false `false→true` audit row — corrected to lock-then-check-then-transition-at-most-once (item 2, scenario 38, new). Round 6's mismatch handling (scenario 36) recorded only the intent-level flag, never the delivery-level processing outcome, leaving a real Gate-A-passed webhook receipt with no corresponding rejection evidence in `payment_webhook_processing_events` — corrected with a new `PROVIDER_ENVIRONMENT_MISMATCH` processing-result value (item 3, scenario 39, new). Round 6's Phase C for the old 12-arg signature (scenario 32) relied on an unbounded, subjective "full observation window" with no hard checkout-disabled gate — corrected to a bounded, provable, checkout-gated sequence (item 4, scenario 32's mitigation updated below, and scenario 40, new). `GATE-FLUTTERWAVE-CREATED-AT-SEMANTICS` (scenario 37) is hardened with an explicit permitted/prohibited boundary distinguishing evidence-gathering work from payment-authority implementation (item 5, scenario 37's row updated below).

**Design-correction round 8 (this revision, surgical — an executability correction, not a redesign):** an eighth review found round 7's own two new mechanisms were themselves unexecutable or under-specified. `flag_webhook_payment_requires_manual_review`'s `IF p_reason_code NOT IN (...) THEN` silently passes a `NULL` reason code, since `NULL NOT IN (...)` evaluates to `NULL`, never `TRUE`, under standard SQL three-valued logic (item 1, scenario 41, new). Round 7's evidence-recording fix for a `provider_environment` mismatch used a raw `INSERT` naming only two of `payment_webhook_processing_events`'s real columns — the real table also requires `provider`/`signature_valid` `NOT NULL` — corrected to reuse the existing `recordProcessingEvent` helper, whose own return contract is corrected to report success/failure explicitly rather than silently swallowing a database error; the handler now returns HTTP 500 (never calling the flag RPC, never returning 200) on evidence-write failure, and checks the flag RPC's own error channel explicitly rather than assuming success (item 2, scenario 39 updated, scenario 42 new).

## Part 1 — Concurrency audit

Ground truth: `acquire_checkout_intent_lease`'s transaction-scoped advisory lock (keyed per `billing_customer_id + offer_id`), together with the `creation_token`/`lease_expires_at` fencing on the `PROVIDER_CREATING` state, is the real safety net for checkout-intent creation (round 2 — see `DATA_CONTRACTS.md` §3 for why an advisory lock alone, released before the external provider call completes, was insufficient on its own); `commit_verified_commercial_payment`'s intent-level `FOR UPDATE` lock plus its customer-level advisory lock (acquired before the licence re-read) are the real safety nets for payment commit. Everything upstream of these (application-level replay pre-checks, the webhook's own status check) remains a fast-path optimization, never the guarantee.

A 500 at either point causes Flutterwave to redeliver; three independently-analyzed starting states (failure before evidence, failure during evidence, failure after evidence but during the flag call) all converge safely on retry, since a retry's own fresh evidence write and `ALREADY_FLAGGED`'s idempotency together cover every case (item 2, `DATA_CONTRACTS.md` §6a's retry-convergence proof) | **MITIGATED by design** |

**Summary:** every concurrency scenario in this table, across all eight correction rounds, is now specified with an atomic, database-enforced mechanism — no scenario is left as "requires application-level work" or "requires a support runbook" for its data-integrity dimension, with one explicitly-noted exception (#40, which is procedural by nature — a release-sequencing gate, not a row-level invariant — and is flagged as such rather than overstated). One residual item (#6, the intent-level commit lock) still needs live-Postgres confirmation that the deployed function's statement ordering matches this specification exactly — that is a verification task for a staging environment, not an open design question. A second, distinct residual item (#37) is not a verification gap but an explicit, named, still-OPEN blocking gate on unproven third-party semantics — no payment-authority implementation depending on it may be approved, merged, or deployed until it is closed, though Phase-0 evidence-gathering work is explicitly permitted in the interim.
