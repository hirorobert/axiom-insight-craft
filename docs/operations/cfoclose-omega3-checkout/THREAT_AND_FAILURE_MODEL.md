# Ω3-CHECKOUT — Threat and Failure Model

Design/audit document. Covers concurrency (Step 6) and failure-state classification (Step 8).

**Design-correction round 1:** re-audited against the corrected atomic checkout-intent design and customer-level commit lock. Scenarios 1, 2, and 13 re-analyzed against the atomic RPC; scenario 6 given a complete design; scenario 8 given a deterministic outcome; two crash-recovery scenarios added; webhook reliability re-classified per the transient/definitive split. "Renewal" throughout means manual, customer-initiated — this design ships a prepaid term licence, never automatic recurring billing (item 8).

**Design-correction round 2:** round 1's single-RPC checkout-intent design (scenarios 1, 2, 13, 14, 15) is superseded by the token-fenced lease protocol (`DATA_CONTRACTS.md` §3) — three new scenarios (live-lease contention, stale-lease takeover, failed-CAS non-disclosure) are added, alongside reconciliation concurrency (`SKIP LOCKED`), offer-activation compare-and-swap, and the corrected provider-selection-ordered platform-state gate.

**Design-correction round 3 (this revision):** the `LEASE_HELD` response contract is corrected from an unbounded 409 to a bounded, 202-with-`Retry-After` client retry protocol (item 8); the reconciliation claim mechanism is corrected from a timestamp-only claim to a durable, token-fenced lease, closing a genuine permanent-stranding risk after a worker crash (item 5) — two new scenarios (21, 22) cover crash recovery at the terminal and non-terminal attempt numbers; a new scenario (23) covers Flutterwave's lookup-by-reference returning multiple matches (item 11); and the reconciliation evidence table reference is corrected from `payment_webhook_processing_events` (structurally incompatible — its `receipt_id` is `NOT NULL`) to the new dedicated `payment_reconciliation_attempts` table (item 4).

## Part 1 — Concurrency audit

Ground truth: `acquire_checkout_intent_lease`'s transaction-scoped advisory lock (keyed per `billing_customer_id + offer_id`), together with the `creation_token`/`lease_expires_at` fencing on the `PROVIDER_CREATING` state, is the real safety net for checkout-intent creation (round 2 — see `DATA_CONTRACTS.md` §3 for why an advisory lock alone, released before the external provider call completes, was insufficient on its own); `commit_verified_commercial_payment`'s intent-level `FOR UPDATE` lock plus its customer-level advisory lock (acquired before the licence re-read) are the real safety nets for payment commit. Everything upstream of these (application-level replay pre-checks, the webhook's own status check) remains a fast-path optimization, never the guarantee.

| # | Scenario | Where the race actually resolves | Mechanism | Verdict |
|---|---|---|---|---|
| 1 | Two browser tabs, same customer, same offer, near-simultaneous checkout request | `acquire_checkout_intent_lease`'s `pg_advisory_xact_lock` on `(billing_customer_id, offer_id)` serializes the two RPC calls; whichever acquires it second sees either a reusable `PENDING` row (`REUSED`) or a still-live `PROVIDER_CREATING` lease (`LEASE_HELD` → 202 `CHECKOUT_IN_PROGRESS` with `Retry-After`, round 3 correction of round 2's 409 choice — item 8; frontend retries briefly, bounded) — never a second concurrent `INSERT` | Transaction-scoped advisory lock + lease status | **MITIGATED** |
| 2 | Two simultaneous checkout-creation requests (double-click) | Identical mechanism to #1 | Same | **MITIGATED** |
| 3 | Repeated payment attempts against the same intent (customer retries after a declined card) | Intent status stays `PENDING` until a webhook resolves it; only one provider attempt can ever reach `commit_verified_commercial_payment` successfully, gated by the intent's own status check | `SELECT ... FOR UPDATE` on the intent inside the commit RPC | **MITIGATED** (unchanged) |
| 4 | Duplicate webhook delivery | `idempotencyKey` UNIQUE, checked first by the commit RPC, returns `ALREADY_COMMITTED` with no mutation | Idempotency key UNIQUE index | **MITIGATED** (unchanged) |
| 5 | Webhook and status-poll racing | `get_checkout_status` is read-only; nothing to race against | None needed | **MITIGATED** (unchanged) |
| 6 | Two worker instances processing the same webhook delivery concurrently | **Now fully specified, not merely flagged for verification:** both attempt `commit_verified_commercial_payment` with the same idempotency key; the intent-level `FOR UPDATE` lock serializes the two transactions; the idempotency-key pre-check runs again immediately after that lock is acquired (not only once, before it) — this ordering is now an explicit, named requirement of the corrected design (`DATA_CONTRACTS.md` §11's re-read-after-lock instruction), closing the TOCTOU gap the prior round could only flag, not resolve, from static analysis alone | Intent-level `FOR UPDATE` + idempotency-key re-check after lock acquisition | **MITIGATED by design; still requires a live-Postgres run to confirm the deployed function matches this specification exactly** — this residual verification step is unavoidable without a database connection in this environment, but it is no longer an open design question |
| 7 | Two successful payments (two different `providerTransactionId`s) racing to commit against the *same* intent | First writer's lock + status transition means the second writer's re-validation of `intent.status` fails with `INTENT_ALREADY_RESOLVED` | `SELECT ... FOR UPDATE` on the intent | **MITIGATED** (unchanged) |
| 8 | Two different, successful intents for the same customer (e.g. MONTHLY then ANNUAL, both paid) | **Corrected — now deterministic, not deferred to a support runbook.** The **new customer-level advisory lock** in `commit_verified_commercial_payment` (`DATA_CONTRACTS.md` §11) serializes the two commits strictly: whichever acquires the lock first closes out the customer's prior licence (if any) and inserts its own period; the second commit, on acquiring the lock, re-reads the now-updated current-licence state and closes out *that* row before inserting its own — both payments are committed, both licence periods exist in the historical record (append-only, never overwritten), and the customer ends up on whichever plan/interval the *second* commit represents, with `effective_start` chained correctly from the first's `effective_end`/closeout point. No exclusion-constraint violation is reachable, because the two commits never execute the closeout-then-insert sequence concurrently. | Customer-level `pg_advisory_xact_lock`, acquired before the licence re-read | **MITIGATED by design** — the *data-integrity* question (can a charge be silently discarded) is closed structurally; the *product* question (the customer probably didn't intend to buy both) remains a support/refund concern, explicitly out of this design's scope, but is no longer a state where the system's own behavior is undefined |
| 9 | Term ends and customer manually checks out again immediately (manual renewal) | `excl_cl_no_overlapping_authoritative_periods` only constrains *overlapping* ACTIVE/GRACE periods; an abutting period (old ends exactly where new begins) does not overlap | GiST EXCLUDE (existing) + customer-level lock (new, item 6) now also covers the case where this "renewal" checkout races against another concurrent commit for the same customer | **MITIGATED** |
| 10 | Manual renewal while status is ACTIVE (customer buys a new term before the current one expires) | Same closeout-then-insert flow, now customer-lock-serialized | GiST EXCLUDE + closeout logic + customer-level lock | **MITIGATED** |
| 11 | Manual renewal while status is GRACE | Identical mechanism to #10; GRACE participates in the closeout lookup identically to ACTIVE | Same | **MITIGATED** |
| 12 | Provider-side retries (Flutterwave retries a failed verify call, or resends a webhook per its own retry policy) | Covered by #4 (idempotency); Gate B is naturally idempotent | Idempotency key UNIQUE | **MITIGATED** |
| 13 | Timeout + client-side retry (the browser's `createCheckoutIntent` call times out but the Edge Function actually completed) | The retried call re-enters `acquire_checkout_intent_lease` for the same customer+offer; if the first attempt already succeeded through to `persist_checkout_provider_result`, the retry gets `REUSED` and the same link; if the first attempt is still genuinely in flight, the retry gets `LEASE_HELD`/202 rather than racing it | Lease protocol | **MITIGATED** |
| 14 | **Crash between provider-link creation and database persistence** — `adapter.createCheckout()` succeeds, Flutterwave returns a real URL, but the process dies before `persist_checkout_provider_result` runs | The row is left `PROVIDER_CREATING` with an unexpired `lease_expires_at` for up to 60 seconds — during that window a concurrent request correctly gets `LEASE_HELD`, never a false reuse or a false supersession. Only once the lease genuinely expires (60s) does the NEXT request's staleness sweep mark it `FAILED` and create a fresh row | 60-second lease TTL + explicit expired-lease-only supersession (`DATA_CONTRACTS.md` §3, round 2 correction of the round-1 CREATED/NULL-url design) | **MITIGATED by design** — the orphaned Flutterwave-side session, if one exists, is never presented to a customer (see scenario 18 below) and expires unused on Flutterwave's own side |
| 15 | Two simultaneous inserts for the same customer+offer racing at the `INSERT` statement itself | Cannot occur: `pg_advisory_xact_lock` is the first statement in `acquire_checkout_intent_lease`, before the staleness sweep, the reuse check, the live-lease check, or the `INSERT` | Transaction-scoped advisory lock covering the entire function body | **MITIGATED by design** |
| 16 (round 2, response contract corrected round 3) | **Live-lease contention** — a second request for the same customer+offer arrives while a first request's `PROVIDER_CREATING` lease is still unexpired (the first is genuinely mid-flight calling Flutterwave) | `acquire_checkout_intent_lease` returns `LEASE_HELD` explicitly — it never steals, never blocks the second request indefinitely, and never creates a second row. The Edge Function returns 202 `CHECKOUT_IN_PROGRESS` with `Retry-After` (item 8, round 3); the frontend retries up to 3 times within a 15-second wall-clock cap, then surfaces a "still processing" message rather than looping indefinitely | Explicit unexpired-lease check, item 3's "never steal a live lease"; bounded client retry, item 8 | **MITIGATED by design** |
| 17 (new, round 2) | **Stale-lease takeover** — a `PROVIDER_CREATING` row's `lease_expires_at` has passed (its original caller crashed or genuinely took over 60 seconds) | The next call's staleness sweep (`UPDATE ... SET status='FAILED' WHERE status='PROVIDER_CREATING' AND lease_expires_at <= now()`) supersedes it deterministically, then proceeds to create a fresh row — this is the ONLY condition under which a `PROVIDER_CREATING` row is ever superseded | Expired-lease-only supersession | **MITIGATED by design** |
| 18 (new, round 2) | **Failed CAS — the original holder's Flutterwave call eventually succeeds, but after its own lease already expired and was superseded** | `persist_checkout_provider_result`'s `UPDATE ... WHERE creation_token = $2 AND status = 'PROVIDER_CREATING'` affects 0 rows (the row is now `FAILED`, owned by nobody, or superseded); the function returns `persisted:false`; the Edge Function returns a 502 to the browser and **never returns the checkout URL**, even though Flutterwave genuinely created a live session for it | Token-based CAS, item 3's "never return a URL after failed CAS" | **MITIGATED by design** — the orphaned session is never reachable by the customer through this flow; if a webhook nonetheless later arrives for that reference, the intent's `FAILED` status causes `authoriseCommit` to reject it as `INTENT_ALREADY_RESOLVED` (evidence preserved, never silently committed, never silently discarded — see `DATA_CONTRACTS.md` §3's orphan-session note) |
| 19 (round 2, claim mechanism corrected round 3) | **Two concurrent reconciliation runs** (a slow prior run still executing when the next `pg_cron` tick fires 5 minutes later) | `claim_stale_checkout_intents_for_reconciliation`'s `FOR UPDATE SKIP LOCKED` means the second run simply skips any row the first run already holds locked and claims a disjoint batch — no blocking, no double-processing, no double-commit attempt (and even a double-commit attempt would be caught by the unchanged idempotency-key mechanism as a final backstop) | `SKIP LOCKED` | **MITIGATED by design** |
| 20 (new, round 2) | **Offer activation/deactivation racing an admin's own stale UI state** (two browser tabs, or a double-submitted admin form, both attempting to flip the same offer's `is_purchasable`) | `admin_set_offer_purchasable`'s expected-state compare-and-swap (`IF v_offer.is_purchasable IS DISTINCT FROM p_expected_current_purchasable THEN RAISE EXCEPTION 'EXPECTED_STATE_MISMATCH'`) rejects the second call outright rather than silently double-applying or silently no-op'ing | `FOR UPDATE` + explicit expected-value comparison (item 4, round 2) | **MITIGATED by design** |
| 21 (new, round 3) | **Reconciliation worker crashes immediately after claiming the terminal (8th) attempt, before completing it** | Round 2's timestamp-only claim would have permanently stranded this row (no further claim possible once `attempt_count = 8`, and no live process to complete it). Round 3's durable lease (`reconciliation_claim_token`/`reconciliation_lease_expires_at`) means the crashed claim's lease simply expires after 2 minutes; the next `pg_cron` tick's claim query's own `terminal` CTE (`DATA_CONTRACTS.md` §7.2) then atomically transitions the row to `FAILED` with full evidence (the crashed attempt's own `CLAIMED` row in `payment_reconciliation_attempts` remains, proving an 8th attempt was made and never completed) — resolved within one `pg_cron` tick (≤5 minutes) of the crash, never left indefinitely | Durable token-fenced lease + atomic claim-or-terminal-transition in one statement | **MITIGATED by design** |
| 22 (new, round 3) | **Reconciliation worker crashes mid-attempt at a NON-terminal attempt number (e.g. attempt 3 of 8)** | Identical mechanism to #21 — the lease expires, the row becomes reclaimable again once its backoff window (computed from the now-expired lease's start time) has passed, and a fresh attempt is made under an incremented attempt number. The crashed attempt's `CLAIMED` evidence row remains, permanently, alongside the eventual real outcome | Durable token-fenced lease | **MITIGATED by design** |
| 23 (new, round 3) | **Flutterwave lookup-by-reference returns multiple transactions for one `saff_reference`** (a genuine provider-side anomaly, e.g. a retried charge under the same reference) | `verifyTransactionByReference` never picks one — returns `AMBIGUOUS_MULTIPLE_TRANSACTIONS_FOR_REFERENCE` explicitly, mirroring `resolve_commercial_offer`'s own AMBIGUOUS-never-guess discipline (`DATA_CONTRACTS.md` §7.4); if this repeats across attempts, the intent eventually reaches terminal-failure escalation for mandatory human review via `admin_billing_lookup` rather than an automatic system ever resolving the ambiguity by guessing | Explicit multi-match rejection, never a "pick the first/newest" heuristic | **MITIGATED by design** |

**Summary:** every concurrency scenario in this table, across both correction rounds, is now specified with an atomic, database-enforced mechanism — no scenario is left as "requires application-level work" or "requires a support runbook" for its data-integrity dimension. One residual item (#6, the intent-level commit lock) still needs live-Postgres confirmation that the deployed function's statement ordering matches this specification exactly — that is a verification task for a staging environment, not an open design question.

## Part 2 — Failure-state classification

Legend: **MITIGATED** = a specific, named mechanism already prevents/handles this, or (for new mechanisms in this design) is now fully specified even though not yet implemented. **WORK** = the mechanism is specified here but requires new code at implementation time (distinguished from "unspecified"). **N/A** = does not apply to this system's design. **UNTESTABLE** = correct behavior is asserted by static source-text proof only; requires a live staging Postgres/Deno run to be considered verified.

| Failure state | Classification | Mechanism / gap |
|---|---|---|
| Unauthenticated user calls checkout | MITIGATED | `validateAuth` rejects with 401 before any other check |
| Invalid plan code | MITIGATED | `resolve_commercial_offer` returns `UNKNOWN`; Edge Function maps to 404 |
| Invalid/missing billing interval | MITIGATED (corrected) | Explicit body-level `IF p_billing_interval IS NULL OR ... NOT IN (...)` check, first statement in the function — not a `NOT NULL` parameter annotation (invalid syntax), not a silent default |
| **Ambiguous plan code across products (new)** | WORK | Closed by the corrected resolver's product-scoped lookup (`DATA_CONTRACTS.md` §1) and the identical fix required in `admin_upsert_commercial_offer` — both are implementation-time changes, specified here, not yet applied |
| Invalid/unrecognized market | MITIGATED | Market is now a server-side literal `'GLOBAL'`, never a browser input — the market CHECK-constraint vocabulary check inside the resolver becomes defense-in-depth against a future internal caller mistake, not a browser-facing validation |
| **Platform state PAYMENTS_DISABLED (new)** | WORK (specified) | New gate, first check after auth in `commercial-create-checkout`: reject with 503 before any offer resolution |
| **Platform state SANDBOX_ONLY / LIVE_ACCEPTANCE reached by an ordinary customer (new)** | WORK (specified) | 403, restricted-identity check |
| **Provider-environment mismatch against the current platform state (new; corrected round 2)** | WORK (specified) | 503 `PROVIDER_ENVIRONMENT_MISMATCH`. Round 1 checked `getConfiguredProviders()[0]` — an arbitrary array element, not necessarily the provider this specific offer will actually use. Round 2 corrects the check to inspect the capability entry for the provider `selectPaymentProvider()` genuinely selected for this offer, evaluated after routing, not before |
| **Reconciliation concurrency — two scheduled runs overlapping (new, round 2)** | MITIGATED by design | `FOR UPDATE SKIP LOCKED` in `claim_stale_checkout_intents_for_reconciliation` — see Part 1, scenario 19 |
| **Offer activation/deactivation double-submit (new, round 2)** | MITIGATED by design | `admin_set_offer_purchasable`'s expected-state CAS — see Part 1, scenario 20 |
| **TZ-market checkout attempt (new, round 2)** | MITIGATED by design, scope decision | `commercial-create-checkout` passes a literal `'GLOBAL'` to `resolve_commercial_checkout_offer` — a TZ-market offer is categorically unreachable via checkout regardless of its `is_purchasable` value. Verified non-regressive because both existing TZ offers are already non-purchasable (`DATA_CONTRACTS.md` §9); this must be re-checked at deploy time, not assumed from this design snapshot |
| **Missing/invalid `commercial_platform_state` row (new)** | WORK (specified) | 503 `PAYMENTS_UNAVAILABLE` — fail closed, never "proceed as if enabled" |
| Inactive offer (`is_active = false`) | MITIGATED | Excluded from the resolver's counting query |
| Non-purchasable offer (`is_purchasable = false`) | MITIGATED, and now the **default state of the two new USD offers at seed time** (item 12) | `NOT_AVAILABLE` until a separate, audited activation step flips the flag |
| Missing offer (zero match) | MITIGATED | `NOT_AVAILABLE`, mapped to 402 |
| Ambiguous offer (post-Ω3-CHECKOUT) | MITIGATED (structurally prevented) | Ω3.0's 5-column uniqueness + exclusion constraints |
| Provider unavailable | MITIGATED | `selectPaymentProvider` returns `PAYMENT_PROVIDER_UNAVAILABLE` explicitly |
| Checkout creation failure (Flutterwave API error/network error) | MITIGATED | `adapter.createCheckout` returns `{success:false}`; the two-step protocol's second `UPDATE` marks the intent `FAILED` |
| **Duplicate checkout-intent creation (corrected)** | MITIGATED | `acquire_checkout_intent_lease`'s advisory lock + reuse/lease logic (item 3, round 2) |
| **PROVIDER_CREATING intent with a live, unexpired lease (crash-window, round 2)** | MITIGATED by design | See Part 1, scenario 16 — never stolen, caller gets `LEASE_HELD` |
| **PROVIDER_CREATING intent with an expired lease (crash recovery, round 2)** | MITIGATED by design | See Part 1, scenario 17 |
| **Provider result persisted after the owning lease already expired (round 2)** | MITIGATED by design | See Part 1, scenario 18 — token-CAS fails, URL never returned |
| Abandoned checkout | MITIGATED | Intent stays `PENDING` until `expires_at`; the atomic RPC's staleness sweep transitions it to `EXPIRED` deterministically on the next relevant call for that customer+offer, rather than relying on an external cron job's clock |
| Expired checkout intent | MITIGATED | `authoriseCommit` rejects `INTENT_EXPIRED` |
| Malformed webhook body | MITIGATED | `normalizeWebhook` returns a neutral `PARSE_ERROR`/`UNKNOWN` event; receipt still recorded first |
| Forged webhook (invalid `verif-hash`) | MITIGATED | Gate A rejects, receipt recorded, no commit |
| Duplicate webhook | MITIGATED | Idempotency-key mechanism |
| Replayed webhook | MITIGATED | Same mechanism, plus a fast-path `REPLAY` pre-check |
| Delayed webhook (past intent expiry) | MITIGATED | `authoriseCommit`'s expiry check |
| **Definitive Gate B failure (mismatch/forgery) (corrected framing)** | MITIGATED | Rejected outright, no commit, no retry — this is a fact about the transaction, not the verification call's reliability (item 7) |
| **Transient Gate B failure (network/5xx/timeout contacting the provider) (new, corrected classification)** | WORK (specified) | Previously folded into "already mitigated" alongside definitive failures — **explicitly not classified that way now**. A distinct `VERIFICATION_TRANSIENT_FAILURE` outcome, a 500 response to Flutterwave (triggering its own redelivery), recorded to `payment_webhook_processing_events` under a new (additive) enum value |
| Amount mismatch | MITIGATED | Bigint comparison at three independent layers |
| Currency mismatch | MITIGATED | Same three layers |
| Reference mismatch | MITIGATED | Ω2-GR1 repair, no fallback to the locally-expected reference |
| Duplicate payment (two provider transactions, one intent) | MITIGATED | See Part 1, scenario 7 |
| **Concurrent commit for the same intent** | MITIGATED, one item UNTESTABLE | See Part 1, scenario 6 |
| **Concurrent commit for two DIFFERENT intents, same customer (corrected classification)** | MITIGATED by design (was: N/A / deferred) | See Part 1, scenario 8 — now data-integrity-closed via the customer-level lock, not merely a support question |
| Successful payment but activation failure (Edge Function crashes after the RPC commits) | MITIGATED | The RPC is transactional; a mid-RPC crash cannot leave a half-committed licence. The customer's independent poll (`PaymentReturn.tsx`) reflects true DB state on its next tick regardless of whether the webhook's own HTTP response ever reached Flutterwave |
| **Paid-but-uncommitted transaction persisting beyond a normal retry window (new)** | WORK (specified) | Reconciliation mechanism, `DATA_CONTRACTS.md` §7 (durable lease §7.2, exact backoff/window §7.3, Flutterwave lookup determinism §7.4, cron auth §7.5) — feeds the same two-gate verification and the same commit RPC, never a lesser-authority shortcut, with outcomes recorded to the dedicated `payment_reconciliation_attempts` evidence table (§7.1), never `payment_webhook_processing_events` (structurally incompatible — its `receipt_id` is `NOT NULL`). Design-only; not implemented |
| Reversed payment | MITIGATED (deliberately conservative) | `record_payment_reversal()` never auto-mutates a licence — always `REVIEW_REQUIRED` |
| Pending payment | MITIGATED | Distinct, non-terminal status |
| Expired payment (provider-side) | MITIGATED | Normalized to `EXPIRED`, never conflated with `FAILED`/`CANCELLED` |
| Cancelled payment | MITIGATED | Distinct terminal state |
| Grace-period customer | MITIGATED | GRACE treated as current/entitled throughout |
| Suspension | MITIGATED | Distinct non-entitled status, admin-only writer |
| **Manual renewal (corrected terminology)** | MITIGATED | See Part 1, scenarios 9–11. Never automatic — always a new, customer-initiated checkout |
| Cancellation | MITIGATED | Distinct terminal licence status |
| Existing PAID customer | MITIGATED | Requirement B; the atomic intent-acquisition and customer-lock changes touch intent/commit mechanics only, not entitlement logic |
| Existing FREE customer | MITIGATED | Unaffected |
| Existing Tanzania customer | MITIGATED | Nothing in this design touches TZ-specific offers or payment methods |
| Historical sandbox offer | MITIGATED | Proven non-purchasable and conflict-free under the 5-column key |
| **Cross-product plan-code ambiguity (new)** | WORK (specified) | See §3a of `COMMERCIAL_ARCHITECTURE_AUDIT.md` and the corrected resolver in `DATA_CONTRACTS.md` §1 |
