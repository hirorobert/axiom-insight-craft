# Ω3-CHECKOUT — Threat and Failure Model

Design/audit document. Covers concurrency (Step 6) and failure-state classification (Step 8).

## Part 1 — Concurrency audit

Ground truth established in `COMMERCIAL_ARCHITECTURE_AUDIT.md` §6–7: `commit_verified_commercial_payment`'s `SELECT ... FOR UPDATE` lock on the checkout-intent row, plus `payment_events.idempotency_key` UNIQUE, are the two real safety nets. Everything upstream of the RPC (application-level replay pre-checks, the webhook's own status check) is a fast-path optimization, not a guarantee — it must never be relied on as the sole protection in the analysis below.

| # | Scenario | Where the race actually resolves | DB locking required? | Verdict |
|---|---|---|---|---|
| 1 | Two browser tabs, same customer, same offer | `commercial-create-checkout`'s new reuse-check (`DATA_CONTRACTS.md` §6) | No new lock — a `SELECT` + reuse is sufficient because the actual charge-granting step is serialized later, at commit time | **REQUIRES WORK** (the reuse-check itself; not a correctness bug today, a UX/hygiene gap — see Failure Table row "duplicate checkout intents") |
| 2 | Two simultaneous checkout-creation requests (different tabs or a double-click) for the same customer+offer | Same as #1 — both would resolve the same offer and could create two intents today; only one can ever be *committed* (see #7), but two live intents is wasted/confusing state | No | **REQUIRES WORK**, same fix as #1 |
| 3 | Repeated payment attempts against the same intent (customer retries after a declined card) | `payment_checkout_intents.status` stays `CREATED`/`PENDING` until a webhook resolves it; each provider attempt is independent at Flutterwave's side, but only one can ever reach `commit_verified_commercial_payment` successfully because the intent's own status is checked and the idempotency key is per-`providerTransactionId` | `SELECT ... FOR UPDATE` on the intent inside the commit RPC | **ALREADY MITIGATED** |
| 4 | Duplicate webhook delivery (Flutterwave retries the same event) | `idempotencyKey = sha256Hex('WEBHOOK:${provider}:${providerTransactionId}:${intentId}')`; `commit_verified_commercial_payment` checks this key FIRST and returns `ALREADY_COMMITTED` with no mutation | Idempotency key UNIQUE index (no row lock needed for the *duplicate*, only for the *first* successful commit) | **ALREADY MITIGATED** (proven by `atomicCommit.test.ts`'s idempotency simulation, though note that test does not import real source — see architecture audit §1.5; the real guarantee is the `payment_events.idempotency_key` UNIQUE constraint plus the RPC's own pre-check, both confirmed directly in the Ω2-G migration text) |
| 5 | Webhook and status-poll racing (customer's browser polls `commercial-payment-status` at the exact moment the webhook commits) | `get_checkout_status` only ever reads `payment_checkout_intents`/`commercial_licences` post-commit state; there is no write path in the poll, so there is nothing to race against — worst case the poll returns pre-commit status once, then post-commit status on the next 3-second tick | No | **ALREADY MITIGATED** (no race is possible because polling is read-only) |
| 6 | Two worker instances processing the same webhook delivery concurrently (e.g. a retried delivery reaching two different Edge Function cold-starts at once) | Both would attempt `commit_verified_commercial_payment` with the same idempotency key; the `FOR UPDATE` lock on the intent row + the UNIQUE constraint on `idempotency_key` mean the second writer either blocks until the first commits (then sees `ALREADY_COMMITTED` via the pre-lock idempotency check, which re-runs after acquiring the lock in `admin_supersede_commercial_offer`'s established double-check pattern) or fails the UNIQUE constraint outright, which the function's `WHEN unique_violation` style handling (established pattern, Ω3.0) would need to translate — **this exact double-check-after-lock pattern is not yet confirmed present inside `commit_verified_commercial_payment` itself** (it is confirmed present in `admin_supersede_commercial_offer`, a sibling function) | `SELECT ... FOR UPDATE` + idempotency UNIQUE | **REQUIRES VERIFICATION** — re-read `commit_verified_commercial_payment`'s exact statement ordering against a live/staging Postgres instance before implementation to confirm the idempotency check re-runs after the lock is acquired, not only before it (a check-then-lock-then-write ordering without a re-check between lock and write is the classic TOCTOU gap this pattern is designed to close elsewhere in the codebase) |
| 7 | Two successful payments (two different `providerTransactionId`s, e.g. a duplicate manual charge) racing to commit against the *same* intent | First writer's `FOR UPDATE` lock + status transition (`CREATED`/`PENDING` → resolved) means the second writer's re-validation of `intent.status` (the RPC's fourth-layer check) fails with `INTENT_ALREADY_RESOLVED` | `SELECT ... FOR UPDATE` on the intent | **ALREADY MITIGATED** |
| 8 | Two different, successful intents for the same customer (e.g. customer buys MONTHLY then, before it activates, buys ANNUAL) | Each intent commits independently and correctly per its own snapshot; `commit_verified_commercial_payment`'s "close out any existing ACTIVE/GRACE licence regardless of plan" step means the second commit to complete will supersede the first's licence period, which is *technically* correct (last successful payment wins) but may not be the *product* outcome the customer expects (they now have an ANNUAL licence but were charged for MONTHLY too, with no refund logic triggered automatically) | Existing `FOR UPDATE` machinery is correct at the DB level; this is a **product/support** question, not a data-integrity one | **NOT APPLICABLE to schema/RPC design** — flagged as a support runbook item, not a Ω3-CHECKOUT implementation gap. The reuse-check in scenario #1/#2 reduces how often this can happen accidentally (same offer) but cannot and should not prevent a customer from deliberately buying a second, different offer. |
| 9 | Renewal immediately after licence end (`effective_end` has just passed) | `excl_cl_no_overlapping_authoritative_periods` (Ω1 GiST EXCLUDE) only constrains *overlapping* ACTIVE/GRACE periods — an abutting period (old ends exactly where new begins) does not overlap (`periodsOverlap` test: "abutting periods ... do NOT overlap"); `commit_verified_commercial_payment`'s closeout logic sets the new period's start appropriately | GiST EXCLUDE (existing) | **ALREADY MITIGATED** |
| 10 | Renewal while status is ACTIVE (customer renews early, before expiry) | Same closeout-then-insert flow as any other successful commit; the existing ACTIVE row's `effective_end` is set to the new period's start, avoiding the overlap the EXCLUDE constraint would otherwise reject | GiST EXCLUDE + closeout logic | **ALREADY MITIGATED** |
| 11 | Renewal while status is GRACE | Identical mechanism to #10 — GRACE participates in the closeout lookup identically to ACTIVE (confirmed: the lookup filters on status IN the "current" set without excluding GRACE) | GiST EXCLUDE + closeout logic | **ALREADY MITIGATED** |
| 12 | Provider-side retries (Flutterwave itself retries a failed verify call, or resends a webhook per its own retry policy) | Covered by #4 (idempotency) and Gate B being naturally idempotent (re-verifying the same `providerTransactionId` returns the same authoritative answer each time, and a second `commit_verified_commercial_payment` call for an already-committed key is a no-op) | Idempotency key UNIQUE | **ALREADY MITIGATED** |
| 13 | Timeout + client-side retry (the browser's `createCheckoutIntent` call times out but the Edge Function actually completed) | Today: a second `createCheckoutIntent` call for the same offer would create a *second* intent (the exact gap #1/#2 close) — the first intent, if it did succeed, becomes an orphaned CREATED row that expires harmlessly after 1 hour (`payment_checkout_intents.expires_at` default) | Reuse-check (§ proposed) | **REQUIRES WORK**, same fix as #1/#2 |

**Summary recommendation:** one application-level change (the reuse-check in `DATA_CONTRACTS.md` §6, applied inside `commercial-create-checkout`) closes scenarios 1, 2, and 13. One verification task (scenario 6) must be completed against a real Postgres instance before implementation is considered complete — this repository has no live DB connection in this environment, so it cannot be resolved by static analysis alone (flagged explicitly, not guessed past). No new database constraint, lock, or migration is needed for concurrency — every other scenario is already correctly handled by the existing `FOR UPDATE` + idempotency-key + GiST-EXCLUDE machinery.

## Part 2 — Failure-state classification

Legend: **MITIGATED** = a specific, named mechanism already prevents/handles this. **WORK** = open gap, addressed in `IMPLEMENTATION_PLAN.md`. **N/A** = does not apply to this system's design. **UNTESTABLE** = correct behavior is asserted by static source-text proof only; requires a live staging Postgres/Deno run to be considered verified (this environment has neither).

| Failure state | Classification | Mechanism / gap |
|---|---|---|
| Unauthenticated user calls checkout | MITIGATED | `validateAuth` rejects with 401 before offer resolution (`authContractRepair.test.ts`) |
| Invalid plan code | MITIGATED | `resolve_commercial_offer` returns `UNKNOWN`; Edge Function maps to 404 |
| Invalid billing interval (proposed field) | WORK | New validation: reject with 400 `INVALID_BILLING_INTERVAL` before calling the resolver — must be added alongside the resolver signature change |
| Invalid/unrecognized market | MITIGATED | `market_code` is CHECK-constrained to a closed vocabulary (`GLOBAL,TZ,MU,GB,EU`); an unrecognized value fails the CHECK, not a silent fallback |
| Inactive offer (`is_active = false`) | MITIGATED | Excluded from the resolver's counting query by construction |
| Non-purchasable offer (`is_purchasable = false`) | MITIGATED | Same — the two existing TZS sandbox rows prove this today |
| Missing offer (zero match) | MITIGATED | `NOT_AVAILABLE`, mapped to 402 by the Edge Function, never a fabricated price |
| Ambiguous offer (post-Ω3-CHECKOUT) | MITIGATED (structurally prevented) | Ω3.0's 5-column uniqueness + exclusion constraints make this state nearly unreachable at the data layer; the resolver still returns `AMBIGUOUS` (never guesses) as defense in depth |
| Provider unavailable (no configured Flutterwave secrets, or a future unsupported currency/market) | MITIGATED | `selectPaymentProvider` returns `PAYMENT_PROVIDER_UNAVAILABLE` explicitly, never fabricates a checkout |
| Checkout creation failure (Flutterwave API error/network error) | MITIGATED | `adapter.createCheckout` returns `{success:false, error}`; intent is updated to FAILED, no checkout URL returned |
| Abandoned checkout (customer never completes payment) | MITIGATED | Intent stays `CREATED`/`PENDING` until `expires_at` (+1h default); no licence change occurs; `PaymentReturn.tsx` times out gracefully after `MAX_POLLS` (40 × 3s = 2 min) with a "still processing" message that explicitly says "do not pay again" |
| Expired checkout intent | MITIGATED | `authoriseCommit` rejects with `INTENT_EXPIRED` if a late webhook arrives after `expires_at`; the RPC's own re-check would also catch this as a defense-in-depth layer |
| Malformed webhook body (unparseable JSON) | MITIGATED | `normalizeWebhook` catches the parse error and returns a `PARSE_ERROR`/`UNKNOWN` neutral event rather than throwing; the immutable receipt is still recorded first regardless |
| Forged webhook (no/invalid `verif-hash`) | MITIGATED | Gate A rejects with `INVALID_SIGNATURE`, receipt still recorded, no commit attempted, 200 returned (avoids retry floods) |
| Duplicate webhook | MITIGATED | See concurrency #4/#12 above |
| Replayed webhook (same event resent well after original processing) | MITIGATED | Same idempotency-key mechanism; additionally an application-level `REPLAY` fast-path check exists (not the safety net, but reduces load on Gate B for the common case) |
| Delayed webhook (arrives after the intent's own `expires_at`) | MITIGATED | `authoriseCommit`'s expiry check |
| Provider verification failure (Gate B rejects) | MITIGATED | `VERIFICATION_FAILED` processing outcome recorded; no commit | 
| Amount mismatch | MITIGATED | Bigint comparison at Gate B, `authoriseCommit`, and the RPC itself (three independent checks) — `AMOUNT_MISMATCH` |
| Currency mismatch | MITIGATED | Same three-layer check — `CURRENCY_MISMATCH` |
| Reference mismatch (tx_ref doesn't match `saff_reference`) | MITIGATED | The Ω2-GR1 repair specifically closes the "missing tx_ref silently accepted" gap (`edgeFlutterwaveGateB.test.ts`, 9 dedicated tests) |
| Duplicate payment (two successful provider transactions for one intent) | MITIGATED | See concurrency #7 |
| Concurrent commit (two commit attempts racing) | MITIGATED, one item UNTESTABLE | See concurrency #6 — the general mechanism is proven, but the exact re-check-after-lock ordering inside `commit_verified_commercial_payment` needs live-DB confirmation |
| Successful payment but activation failure (commit RPC succeeds at the DB level but the Edge Function crashes before returning) | WORK (needs explicit handling, not currently proven) | The RPC itself is transactional (licence insert + audit row in one function invocation), so a mid-RPC crash cannot leave a half-committed licence — Postgres transaction semantics cover this. What is NOT explicitly proven is what the *customer* sees if the Edge Function process dies after the RPC commits but before the HTTP response is sent: the webhook is asynchronous from the customer's perspective (`PaymentReturn.tsx` polls independently), so the customer's poll will correctly show CONFIRMED on its next tick regardless of whether the webhook's own HTTP response ever reached Flutterwave — Flutterwave would simply retry the webhook delivery (covered by idempotency), so this resolves itself, but should be called out explicitly as a "commit is authoritative independent of webhook response delivery" design property in the acceptance test (`ACCEPTANCE_MATRIX.md`) rather than left implicit |
| Reversed payment | MITIGATED (deliberately conservative) | `record_payment_reversal()` never auto-mutates a licence — always `REVIEW_REQUIRED`, human-in-the-loop by design |
| Pending payment | MITIGATED | `PENDING` is a distinct, non-terminal `PaymentStatus`; no commit occurs until `SUCCEEDED` |
| Expired payment (provider-side expiry distinct from intent expiry) | MITIGATED | Normalized to `EXPIRED` status, never conflated with `FAILED` or `CANCELLED` |
| Cancelled payment | MITIGATED | Distinct terminal state, surfaced to `PaymentReturn.tsx`'s `CANCELLED` phase |
| Grace-period customer | MITIGATED | GRACE treated as current/entitled throughout (`entitlementContract.ts`, `classifyEntitlement`) |
| Suspension | MITIGATED | `SUSPENDED` is a distinct non-entitled status; `admin_transition_licence_status` is the only writer |
| Renewal | MITIGATED | See concurrency #9–11 |
| Cancellation | MITIGATED | Distinct terminal licence status, never conflated with EXPIRED |
| Existing PAID customer (interacting with this design) | MITIGATED | Requirement L in the architecture audit; the reuse-check (scenario #1/#2 fix) does not change existing-PAID-customer behavior — it only affects intent *creation*, not licence state |
| Existing FREE customer | MITIGATED | Requirement K |
| Existing Tanzania customer | MITIGATED | Requirement M — nothing in this design touches TZ-specific offers or payment methods |
| Historical sandbox offer | MITIGATED | Requirement N — proven non-purchasable and conflict-free under the new 5-column key (audit §5) |
