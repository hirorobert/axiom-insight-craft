# Ω3-CHECKOUT — Acceptance Matrix

Design document — defines the tests that must pass on a real staging environment before Ω3-CHECKOUT is considered implemented. None of these have been run; this environment has no live Postgres/Deno connection.

**Design-correction round 1:** expanded per independent review (item 13) to cover the corrected atomic checkout-intent design, the customer-level commit lock, platform-state enforcement, product binding, the removed `marketCode` contract, and manual-renewal (not subscription) framing.

**Design-correction round 2:** §1/§3/§4 corrected for the token-fenced lease protocol (replacing the round-1 single-RPC design) and the corrected offer-activation RPC; §8 added executable tests for every round-2 mechanism (item 10).

**Design-correction round 3:** corrected the `LEASE_HELD` contract from a bare 409 to a bounded 202/`Retry-After` client-retry protocol; corrected the failed-CAS test's column name to the real `provider_checkout_url`; corrected the transient-constraint test to reflect that reconciliation outcomes live in a NEW dedicated table; added tests for fail-closed provider-capability resolution, reconciliation crash recovery, `admin_supersede_commercial_offer` product scoping, Flutterwave lookup-by-reference determinism, and cron-secret verification/rotation; added a new §9 (now §10) requiring executable migration-replay acceptance (item 12).

**Design-correction round 4:** corrected §3 test 5 ("Expired intent") for the new provider-timestamp-based expiry check; corrected §1's precondition wording. New §9 added twelve executable tests for: sandbox/production `provider_environment` isolation on reuse, offer-deactivation-races-acquisition, provider-restriction mismatch, payment-before-expiry-with-delayed-webhook, unpaid-intent-after-expiry, crash-between-claim-and-worker-start, crash-on-the-final-attempt, stale-worker-terminalization-after-success, backoff-from-actual-completion, missing-project-URL, and Vault/Edge-secret-mismatch.

**Design-correction round 5 (this revision, surgical):** §3 test 5's obsolete `INTENT_EXPIRED` expectation is gone (superseded by round 4's own correction, kept accurate here). §8 tests 16/17 corrected to the ONE canonical retry contract (`maxAttempts=3` = 1 initial + 2 retries, never a "4th observed response" — High 2A); two new tests (16b, 17b) added for exact-cap exhaustion and full `Retry-After` sanitization. §9 test 18's obsolete "`FAILED` via a terminal CTE" expectation is removed, replaced with the one canonical manual-review outcome shared with §9 test 8 (High 2B). New §10 adds twelve executable tests directly covering Blockers 1–6: `PENDING` never auto-expiring, the corrected non-mutating late-payment rejection, `requires_manual_review` semantics, the now-genuinely-executable crashed-terminal-attempt sweep, `billing_audit_events` field population, the claim RPC's actual composite return shape, dual-environment credential isolation (both checkout-time and webhook-routing-time), and staging/production cross-targeting rejection. §11 (migration replay) gains an explicit 16-point coverage checklist mapping every item in the mission's own "Required Executable Validation Design" list to a specific test.

## 1. Staging acceptance — MONTHLY path

Precondition: the two USD offers exist as `is_purchasable = false` (item 12) and have been separately, explicitly activated (`is_purchasable = true`) via `admin_set_offer_purchasable` as its own audited step (`DATA_CONTRACTS.md` §4 — corrected in round 2; `admin_supersede_commercial_offer` cannot toggle an existing row's flag and is not used for this); `commercial_platform_state` is at least `SANDBOX_ONLY`; Flutterwave sandbox secrets are configured.

| Step | Action | Expected server-verifiable outcome |
|---|---|---|
| 1 | Sign up a fresh FREE user | `billing_customers` row auto-provisioned; `commercial_licences` shows FREE/ACTIVE |
| 2 | Navigate to `/pricing`, select MONTHLY | Display reads USD 49/month, sourced from `resolve_commercial_offer(PAID, MONTHLY)` (no market argument from the browser — `DATA_CONTRACTS.md` §2) once checkout is enabled here |
| 3 | Click checkout CTA | Request body is exactly `{planCode, billingInterval}` — verified by inspecting the actual network request, not just the code (§8 below); `commercial-create-checkout` returns a real Flutterwave sandbox `checkoutUrl`; `payment_checkout_intents` row created via `acquire_checkout_intent_lease` (status transitions `PROVIDER_CREATING` → `PENDING` via `persist_checkout_provider_result`'s token-CAS) with `billing_interval='MONTHLY'`, `expected_amount_minor=4900`, `currency_code='USD'` |
| 4 | Complete payment in Flutterwave sandbox | Webhook receipt inserted; Gate A passes; Gate B's independent `verifyTransaction` call confirms amount/currency/reference |
| 5 | — | `commit_verified_commercial_payment` acquires the customer-level lock, transitions licence to PAID/ACTIVE, `effective_end` = now + 1 month |
| 6 | Navigate to Settings | Plan badge "CFOClose Professional", licence status "Active", correct effective-through date, entitlements list includes `MAONO_INTELLIGENCE`/`MULTI_COMPANY`/etc.; **no language anywhere implies automatic renewal** (item 8) — copy must read as a fixed-term licence |
| 7 | Check `billing_audit_events` | Audit row documents the FREE→PAID transition |

## 3. Staging acceptance — adversarial/edge cases (both intervals)

| # | Scenario | Required server-verifiable outcome |
|---|---|---|
| 1 | Duplicate webhook delivery | `ALREADY_COMMITTED`/`REPLAY`; `commercial_licences` unchanged; no second period created |
| 2 | Replay days later | Same — idempotency key is not time-bound |
| 3 | Amount mismatch (provider-side true value differs from the intent's snapshot) | `AMOUNT_MISMATCH`, no commit |
| 4 | Currency mismatch | `CURRENCY_MISMATCH`, no commit |
| 5 | Expired intent, payment ALSO after expiry (corrected, round 4 — see §9 tests 5–6 for the payment-before-expiry and never-paid cases specifically) | `PAYMENT_AFTER_INTENT_EXPIRY`, no commit — `authoriseCommit` compares the provider's own payment timestamp against `expires_at`, not wall-clock verification time (`DATA_CONTRACTS.md` §7.0) |
| 6 | Invalid interval value sent directly to the Edge Function (bypassing the UI) | 400/`UNKNOWN_OR_MISSING_BILLING_INTERVAL`, no offer resolution attempted |
| 7 | `marketCode` sent in the request body anyway (a client bypassing the UI, or a stale cached frontend build) | **Must be silently ignored, never honored** — the Edge Function's request-parsing must not read a `marketCode` field even if present; market remains the literal `'GLOBAL'` regardless of what the body contains. This is a new, explicit test closing item 2's requirement that market is not merely "usually GLOBAL" but structurally unreachable as a client input. |
| 8 | Existing PAID customer attempts to buy the same plan/interval again | Blocked client-side by `shouldShowUpgradeAction`, or if reached directly, results in a licence closeout+reinsert leaving the customer PAID/ACTIVE with an updated `effective_end` — never a downgrade, never a duplicate ACTIVE row |
| 9 | Existing Tanzania (TZ market, TZS currency) customer flow | Entirely unaffected — regression check |

## 4. Concurrency acceptance (item 13 — new)

| # | Scenario | Required server-verifiable outcome |
|---|---|---|
| 1 | **Simultaneous checkout creation** — fire two `commercial-create-checkout` requests for the same authenticated customer and the same offer within the same event loop tick (staging load-test harness, not two manual clicks) | Exactly one `payment_checkout_intents` row exists for the pair afterward; the winning request's response is served to whichever call actually completed the flow; the second call observes either `REUSED` (if the first had already reached `PENDING`) or a 202 `CHECKOUT_IN_PROGRESS` with `Retry-After` (item 8, round 3 — if the first was still `PROVIDER_CREATING`) — never a second row, never a bare 409 |
| 2 | **Crash between provider creation and database persistence** — in a staging harness, forcibly kill the Edge Function process (or inject a fault) after `adapter.createCheckout()` returns successfully but before `persist_checkout_provider_result` executes | The row is left `PROVIDER_CREATING` with a live lease for up to 60 seconds (during which a concurrent attempt correctly gets `LEASE_HELD`, not a false reuse); only once the lease expires does the next attempt's staleness sweep mark it `FAILED` and create a fresh, working intent — verify no window exists where a stale or absent URL is ever served |
| 3 | **Two different successful intents for the same customer** — complete payment on a MONTHLY checkout, then before/around the same time complete payment on a separately-created ANNUAL checkout for the same customer | Both payments commit (`COMMITTED`, not `ALREADY_COMMITTED` for either — they are genuinely different transactions); `commercial_licences` shows two historical rows, non-overlapping, with the second's `effective_start` correctly chained from the first's closeout; the customer's *current* licence reflects whichever commit's lock-acquisition order was second; no exclusion-constraint error appears in any log |
| 4 | **Transient provider-verification outage and recovery** — in a staging harness, make the Flutterwave verify endpoint return a 503/timeout for one webhook delivery attempt, then allow a subsequent (Flutterwave-initiated or reconciliation-driven) attempt to succeed | The first attempt is recorded as `VERIFICATION_TRANSIENT_FAILURE` (not folded into a generic rejected bucket) and the webhook handler returns 500 (not 200) to trigger Flutterwave's redelivery; the second, successful attempt commits normally via the unchanged Gate A/B/commit path |

## 11. Executable migration-replay acceptance (item 12 — new, round 3)

**Corrected requirement:** items 15–22 above (and, in spirit, every SQL-level test throughout this package) are stated as if a test could simply assert a described outcome — but this repository's entire existing commercial test suite (`edgeMoney.test.ts`, `globalCommerceModel.test.ts`, `omega3_0FoundationMigration.test.ts`, and every other file with a "NON-EXECUTABLE DB BEHAVIOR NOTICE" header) is explicit that it has **no live Postgres connection** and proves only static source-text shape, never actual execution. Round 3's own schema-verification findings (`COMMERCIAL_ARCHITECTURE_AUDIT.md` §9) exist precisely BECAUSE static text review missed an executable defect (the nonexistent `checkout_url` column, the missing `NOT NULL` columns) that a real migration replay would have caught immediately as a constraint-violation error. **Static-source-text review is therefore proven, by this design package's own history, to be an insufficient acceptance method for the SQL surface this design introduces.**

**Required, not optional, before implementation is considered acceptance-tested:** a dedicated, executable migration-replay environment — distinct from the existing Vitest static-analysis suite — that:
1. Spins up a real, ephemeral Postgres instance (the Supabase CLI's own local dev stack, `supabase start`, is the natural choice here since it already applies this repository's exact migration set and Auth/RLS configuration — no new tooling class needs to be adopted, only actually invoked for this purpose, which this repository does not currently do in any automated test run);
2. Applies every migration file in `supabase/migrations/`, in order, including this design's own new Phase A migration, and asserts the apply succeeds with zero errors — this alone would have caught the `checkout_url`/`NOT NULL` defects mechanically, immediately, with no human review required;
3. Executes real `INSERT`/`UPDATE`/`SELECT`/RPC calls against the live schema for every test in items 15–22 above, and for the executable subset of §4 (concurrency), §5 (platform-state), and §6 (product-binding) above, asserting on real returned rows and real Postgres error codes — not on regular-expression matches against SQL source text;
4. Tears down the ephemeral instance after the run, so this is a CI-suitable, repeatable, isolated acceptance gate, not a shared, stateful staging dependency.

This is a **new capability this repository does not have today**, not a reframing of existing tests — implementing it is itself an implementation-adjacent task (setting up the harness) that should be scoped and reviewed like any other infrastructure change, separately from the Ω3-CHECKOUT feature code itself, but it is a **precondition** for claiming any of this design's SQL has been acceptance-tested rather than merely reviewed.
