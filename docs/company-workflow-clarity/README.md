# Company creation and reporting orientation

The directory is the account home. Add company expands the existing company form in place; Cancel asks before discarding entered values. A confirmed company save collapses the form and refreshes the server-owned directory and capacity. The new company is listed as a saved setup draft. It does not start an engagement or navigate into reporting. The legacy /companies/new URL remains usable without a workflow rail and returns to the directory after saving.

Existing company/period rows and saved drafts have a clear Open workspace action. Opening is read-only; the existing explicit, idempotent service-start command remains separate. No permission, plan, mandate, period, certification or financial calculation contract is changed.

The company overview shows ordered rows derived from the same authorised, released workbench model as task navigation. Each stage explains its purpose and exposes its available tasks. The next action is derived by the existing engines. Reporting groups remain absent without server enablement, and their completion is never inferred from trial balance completion. Trial Balance uses the header's status wording, including earlier-engine certification, rather than a generic Complete label. Company details/settings and other available tools sit outside the sequential reporting stages. The overview omits duplicate rail navigation; task pages retain it.

Workspace purpose is edited in Company settings rather than an unexplained directory ellipsis. The editor reads the latest append-only event, starts with that value (or an explicit Not stated), writes through the existing owner-only set_workspace_purpose RPC, and reads back the latest event before confirming success. Lost responses are reconciled by that read. Unconfirmed saves keep the selection and reason. Dirty/busy metadata participates in the existing management navigation guard and company form cancellation. No schema changes.

Validation: complete Vitest suite, TypeScript application check, production build, lint and isolated desktop/mobile browser journeys. The browser journey covers inline cancellation/discard, failure before company creation, lost response after company creation, retry without duplicate creation, saved company selection without a service mutation, explicit service start, existing setup/upload/recovery checks, purpose-save failure and lost response with readback, reopening after refresh, gated reporting rows and horizontal bounds. Fixtures are simulated; real backend contracts belong to CI's local Supabase and disposable PostgreSQL jobs. No production writes, merge or publishing are part of this change.
