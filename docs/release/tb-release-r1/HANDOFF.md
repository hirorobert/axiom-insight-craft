## Why wrappers

Lovable's migration tool accepts pasted SQL text and cannot compare it with a repository file. Each of the four approved migrations is therefore submitted as its **self-checking release wrapper**, using the same mechanism Lovable applied for hosted journal entries 34–57:

- **Verification is inside the database.** A wrapper is ONE `DO` statement that carries the migration's exact committed bytes. Before any statement of the migration runs, PostgreSQL recomputes the enclosed payload's byte count and **full SHA-256**. On any difference — a lost byte, CRLF damage or truncation — it raises `RELEASE_PAYLOAD_MISMATCH` (SQLSTATE 55000) and **nothing changes**. Lovable's own verification is therefore not relied on.
- **Atomic.** It is one statement, so a failure anywhere inside the migration rolls the whole migration back, under any executor.
- **The canonical journal is preserved.** Lovable's migrator records one `drizzle.__drizzle_migrations` row per wrapper, whose hash is the SHA-256 of the submitted text. That hash must equal the registered wrapper identity below (`scripts/ci/releaseJournal.mjs` `SUBMISSION_FORMS`), which is how entries 34–57 were recorded and mirrored.
- **The approved SQL is unchanged.** The wrappers are generated by `scripts/release/selfCheckingWrapper.mjs` from the git objects at `365b370`. `node scripts/release/selfCheckingWrapper.mjs --check` re-derives them byte for byte.
- **Nothing else is replayed.** Only these four, in this order.
- **Proof.** `scripts/db-proof/selfCheckingWrappers.mjs` with `RELEASE_BATCH=tb-release-r1` passed 107/107 on PostgreSQL 16 (CI runs the same on 17). It covers:
  - every damaged-text refusal, before any DDL;
  - early and late failures injected inside each migration, fully rolled back with no journal row;
  - autocommit and the hosted-executor model;
  - a repeated application, refused;
  - the read-only postcondition;
  - drizzle-orm's real `migrate()`.

No direct database connection is used. Production is reachable only through Lovable, and running the files outside Lovable's migrator would bypass the canonical journal. No credential is needed or requested.

## A1/A2 disposition (before any write)

Run `docs/release/tb-release-r1/impactDisposition.sql` in `BEGIN TRANSACTION READ ONLY; … ROLLBACK;`. Age alone is not evidence. Every A1 row (an unfinished check attempt) and every A2 row (an upload never certified) is classified **only from recorded evidence**.

**A1 classes:**

| Class | Evidence |
|---|---|
| `in_flight` | running, with a live lease |
| `later_certified` | a certification of the same upload recorded after the attempt; a failed attempt writes none |
| `concurrency_control` | the engine's own stale or duplicate fences refused it |
| `release_drain` | abandoned by the recorded S2/E2 cut-over drain (`DRAINED_AT_CUTOVER`) |
| `upload_not_current` | the upload is no longer the current one |
| `explicit_failure` | a recorded terminal error code |
| `capacity_bound_candidate` | `LEASE_EXPIRED`, the upload still active and never certified — the pattern repair A fixes |

**A2 classes:**

| Class | Evidence |
|---|---|
| `not_current` | the upload is retired, superseded or discarded |
| `never_checked` | no check was ever run |
| `refused_on_read` | blocked with zero accounts read |
| `completed_uncertified_outcome` | a check completed with a recorded outcome that is not a certification |
| `capacity_bound_candidate` | one of its attempts is an A1 capacity-bound candidate |
| `attempts_explained` | every unfinished attempt falls in an explained A1 class |

**Rules:**
- **Any `unexplained` row: stop and report it.**
- `capacity_bound_candidate` rows do **not** block the release: they are exactly what generation 6 fixes. Record them privately. After the release, the owner re-checks each listed upload, creating a NEW run; nothing is edited.
- Every other class is dispositioned by its recorded evidence and needs no action.
- Records name company and upload ids: keep them private. This repository is public.

## Permission checks — how they execute

The three outstanding permission checks, plus every other post-migration check, are in `docs/release/tb-release-r1/postcondition.sql`. It is read-only and runs in `BEGIN TRANSACTION READ ONLY; … ROLLBACK;`. The three:
1. the internal helpers `tbu_refused_replacement_block(uuid)` and `tbu_upload_dependent_evidence(uuid)` are not executable by `authenticated` or `anon`;
2. `tb_certification_findings_supported()` is present and true, and only `service_role` may call it;
3. clients have no write privilege on `tb_certification_findings` or the draft tables.

Each check is a catalog `has_function_privilege`/`has_table_privilege` evaluation, so it needs no role switch and no signed-in user. The file raises on the first violation and ends with `NOTICE 'POSTCONDITION OK.'`. It also verifies:
- the account-identity end state, by definition;
- the restore branches;
- the client RPC grants.
