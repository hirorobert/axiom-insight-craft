## 3. Authorization ordering contract (finding 1)
- **Admission:** acquisition of the locks below by `_ipsas_authorize_mutation`, then a fresh re-judgement of authority on a READ COMMITTED snapshot, after the mutation's request and company-period locks and **before** any replay lookup or write, in all five RPCs.
- **Guarantee:** from admission until the mutation's transaction commits, no withdrawal of an authority input completes. A withdrawal that committed before admission is seen by the re-judgement (`forbidden`, `feature_disabled`, `framework_not_ipsas_accrual`). A mutation therefore never records a write under authority withdrawn before its commit.
- **How:** member-capability advisory lock (shared); plan, named-user seats and framework locks (shared); rollout keys **try-locked and never waited for** (open and close take them in opposite orders; unavailable means `authority_changing`); `FOR SHARE` row locks on the person's membership row, open capability rows and the company row (writers' UPDATE/DELETE wait); `lock_timeout` 5 s as an operational protection (not what orders anything).
- **Framework change:** `set_company_reporting_framework` refuses `FRAMEWORK_LOCKED` once a certified trial balance or report exists, so at the mutation level it cannot race a certified company; it is proven at the helper level on an uncertified company.
- **Not claimed:** a clock-based expiry is not a writer; a future writer that takes none of these keys and updates none of these rows is not covered; the readers (`ipsas_*_context`) refuse as soon as a withdrawal commits.

## 4. Download issuance: transaction ordering and response-delivery contract (finding 3, re-review)
`precheck (ordinary read, orders nothing) -> sign (Storage, outside any transaction) -> DECIDE (one database transaction) -> return the link only if the decision committed as issued`.

**The decision** (`decide_trial_balance_source_download_issuance`, service role only): in one READ COMMITTED transaction it (a) takes the locks of every writer of the authority inputs, (b) re-judges `workspace_authority_basis(user, workspace, 'manage_source_files')` on a fresh statement snapshot, (c) refuses unless the signed link is provably still valid by the database clock (its conservative floor has not passed), (d) inserts the decision row. **The commit of that transaction is the ordering point**; nothing else is called one. A lock that cannot be had in 5 s returns `unavailable` (nothing recorded, no link, safe to retry).

**Writers found by reading `workspace_authority_basis` and every function/trigger that changes what it reads, and how each is ordered:**
| Authority input | Writers | Ordering with the decision |
|---|---|---|
| open explicit grant | `revoke_workspace_capability`; `firm_members_revoke_workspace_grants` (member removal / re-point) | decision holds `FOR SHARE` on the open grant row to commit: the UPDATE waits (a revoker already holding the row makes the decision wait, re-read, and see the revocation) |
| current plan | licence and entitlement-override writers (trigger takes `cfoclose.plan:<account>` exclusively) | plan advisory lock, shared in the decision |
| named-user seats / billing suspension | seat and suspension writers (`cfoclose.named_user_seats:<account>`) | seats advisory lock, shared, after the plan key (the writers' order) |
| workspace owner / row | an owner change is an UPDATE of the `companies` row | `FOR SHARE` on the company row |
Lock order: plan (S) -> seats (S) -> grant row (S) -> company row (S). `revoke_workspace_capability` takes the company row (S) then updates the grant row; shared locks do not conflict, so no cycle exists. The membership row is not read by the predicate and is not locked. The seat-wall trigger on grants returns before its seats lock for a plain revoke, so a revoker never holds a grant row while waiting for the seats key. A never-member collaborator has no membership row: the protocol needs none, and their access is unaffected by anyone else's removal (proven).

**The two orderings (both proven with barriers, never sleeps):**
- *Withdrawal commits first* (before the decision, or holding its locks first): the decision records `withdrawn_before_issue`; no `issued` row exists; the response is 403 and the minted link is discarded unseen and never logged.
- *The decision commits first*: the writer must wait for it, so the withdrawal is ordered after the issuance; the link may be delivered afterwards. **Response delivery after a later withdrawal is permitted by this contract**; the link is a bearer credential until its own expiry.

**Separate, documented limitations:** a link ALREADY returned stays valid until its Storage expiry (Storage cannot revoke one signed URL); a clock-based plan expiry is not a writer; a new writer that touches none of the keys above is not covered; the function host's clock and the database clock can differ (signing times are recorded as the host's readings, the freshness comparison uses the database clock); Storage's signing behaviour is exercised only by the real-stack CI job, not by the disposable-database proof.

## 6. Audit semantics, expiry source and what is still undecided
- **What a record is.** `issued` = an authorised issuance decision was committed (the right held at the commit and the signed link was not past its conservative validity floor). It is **not** evidence that the response reached the caller or that the file was downloaded; the bytes go from Storage to the browser, which the function cannot observe, and no browser report is treated as evidence. A response that fails or a caller that disconnects after the decision leaves the row exactly as committed; nothing updates it. Other outcomes: `denied` (the precheck refused a caller who named a real upload of a real company), `withdrawn_before_issue`, `expired_before_issue`. Unauthenticated calls and requests naming an unknown upload or another company's are not recorded.
- **Expiry: exact versus estimated.** `link_expiry_kind = signer_exact`: the `exp` claim of the link Storage signed was read (read, not verified, never stored); `link_expiry_exact_at` holds it and floor = exact = ceiling. `estimated_bounds`: the exact expiry is **unknown**, `link_expiry_exact_at` is NULL, and the expiry lies between `link_valid_until_floor_at` (signing START + requested lifetime: the earliest it can expire, since Storage fixes `exp` at some instant between signing start and completion) and `link_expiry_ceiling_at` (signing COMPLETION + lifetime: the latest). **Only the floor may be used to say a link is still valid** (`expired_before_issue` when it has passed); the ceiling states residual access and is never a validity test. Both bounds are computed inside the decision; the caller cannot supply them, and table constraints pin an estimate to its derivation. Never "decision time + 60 s". **Real Storage:** the real-stack CI journey checks, on a link signed by real Storage, that the stored kind is `signer_exact`, that the token's `exp - iat` equals the requested lifetime, that `iat` lies inside the interval the function measured, and therefore that floor <= exp <= ceiling, i.e. that the estimate would have been sound against the real signer.
- **What is stored.** Actor, company, upload, outcome, signing start/completion (function-host clock), requested lifetime, expiry kind, exact expiry (when known), floor, ceiling, the recorded fingerprint, the database clock at the decision. **Never a URL, token or path.**
- **Implemented reader restrictions (not an accepted policy).** The workspace owner may read the workspace's rows (RLS); the service role has SELECT only; no other role can; append-only (update/delete/truncate refused). The only writers are `decide_...` and `record_..._denial` (service role execute only).
- **Policy decisions still required before the audit requirement can be called complete:** who besides the owner may read (administrators, auditors, the actor); retention period and deletion rules; whether other-company or unknown-upload attempts should be recorded; whether denials are retained for the same period; whether delivery evidence is wanted at all (it would need Storage access logs, which are not available here); clock-skew tolerance between the function host and the database. None is assumed.
