## What each apply refuses (and rolls back, stage state included)

Wrong or extra journal head (the exact predecessor row, by hash, must be the newest row); a missing prerequisite the source builds on;
the previous batch not consumed (a journal row alone does not prove it); the batch already consumed; ANY object the source creates
already existing (rfr-2: the contra column); a staged body whose length or hash differs from the pin (re-hashed at apply time, the
stored metadata is not trusted); the source not leaving its target installed; an unexpected privilege on the installed objects
(anon reaching anything new, a client role writing a new table, authenticated executing `fs_publication_blockers`); the compiler
receipt pin or receipt function changed; a changed preserved row (31 tables: the earlier transports' set plus `account_mappings`
— projected without the new nullable `is_contra_account` key — `account_review_decisions`, `financial_statement_reports`,
`financial_statement_publications`, `fs_first_period_declarations`, `financial_statements_rollout_companies`,
`fs_server_compilations`). Each source's own PREFLIGHT and POSTCONDITION blocks run unchanged inside the apply (the exact bytes are
executed), so the original preconditions and postconditions are preserved.

Every source sets its own `search_path`; the apply pins `pg_catalog, public` for the source and restores the ORIGINAL path at
SESSION level afterwards, so the source's SET cannot outlive the commit on the migrator's connection.
