## 1. Why this path

This repository allows exactly one record of hosted application: Lovable's Drizzle apply journal (`drizzle/migrations/`,
`drizzle.__drizzle_migrations`; CLAUDE.md §9.4). The same section forbids `drizzle-kit push` and `drizzle-kit migrate`.

The runner therefore does **not** run drizzle-kit and does **not** create another journal. It writes into the
established journal exactly the row drizzle-orm 0.45.2 (`PgDialect.migrate`) writes for an entry:
- `hash` = SHA-256 of the entry file text (= the candidate's SHA-256, because the entry is the source verbatim);
- `created_at` = the entry's journal `when`.

As in drizzle-orm, the row is written in the same transaction as the SQL.

What drizzle-orm's migrator lacks, and the runner adds:

| Concern | drizzle-orm 0.45.2 migrator | Runner |
|---|---|---|
| Candidate integrity | none | exact bytes + SHA-256 + clean UTF-8 + no statement-breakpoint, before connecting |
| Target identity | the URL only | project ref in the URL (exact Supabase host, or pooler user) + `--expect-system-id` (the database's own `system_identifier`) + journal lineage (last entry must be 0025, hash `621f55c3…`, `created_at` `1790920391757`) |
| Concurrency | none: the "last applied" read happens outside its transaction | `pg_advisory_xact_lock(hashtextextended('cfoclose:hosted-migration-apply', 0))` + `LOCK TABLE drizzle.__drizzle_migrations IN SHARE ROW EXCLUSIVE MODE` + re-check under the locks |
| Timeouts | none | `lock_timeout` (default 5s), `statement_timeout` (default 120s), `idle_in_transaction_session_timeout` (default 120s) |
| Atomicity | SQL + row in one transaction | the same, plus postconditions re-verified inside the transaction before COMMIT |
| Outcomes | applied or skipped, silently | UNAPPLIED, APPLIED, ALREADY_APPLIED, CONFLICT, BUSY, FAILED, UNCERTAIN |

## 2. Operator requirements

- **Who:** the holder of the hosted migration connection (`LOVABLE_DB_MIGRATION_URL`), i.e. Lovable or the owner through Lovable.
  - The connecting role must own the existing RPCs, as on the source chain (`postgres`): `CREATE OR REPLACE` keeps their owner and grants.
- **Software:** Node.js ≥ 20, a checkout of `d03a0dd` (or this branch), `bun install --frozen-lockfile` (Bun 1.3.14).
  - The runner's only dependency is `postgres@3.4.9`, from the committed lockfile.
- **Quiet period:** no other migration may run, and Lovable's own tracked runner must not run, during the window.
  - Lovable's runner takes neither lock; see §7, item 3.
- **No secrets on the command line.** The URL is read from the environment and never printed.

The `when` in the repository must equal the recorded `created_at`. Otherwise drizzle would consider the entry unapplied
(if the repository `when` is larger) or skip a later one.

### What one `apply` transaction does, in order
1. `SET LOCAL` lock, statement and idle timeouts.
2. `pg_advisory_xact_lock` (bounded by `lock_timeout`).
3. `LOCK TABLE drizzle.__drizzle_migrations IN SHARE ROW EXCLUSIVE MODE`.
4. Re-inspect and re-classify under the locks:
   - ALREADY_APPLIED → return without writing;
   - anything but UNAPPLIED → CONFLICT, without writing.
5. Execute the approved SQL verbatim, as one batch.
6. `INSERT INTO drizzle.__drizzle_migrations ("hash","created_at") VALUES (<sha256>, <when>)`.
7. Re-inspect inside the transaction; every postcondition must hold, or the transaction rolls back.
8. COMMIT.
9. A separate read-only verification.

### Postconditions checked
- `capability_customer_available(text)`: **IMMUTABLE**, not a definer.
- `assert_capability_available(text)`: **STABLE**, not a definer.
- `refuse_withheld_service_grant()`: **VOLATILE**, SECURITY DEFINER.
- All three: `search_path=pg_catalog, public`, and an ACL of exactly `{owner=X/owner}`. No `PUBLIC`, anon, authenticated or service_role EXECUTE.
- Trigger `trg_refuse_withheld_service_grant` on `public.engagement_mandate_events`: `tgtype = 5` (AFTER INSERT FOR EACH ROW), enabled, calling that function.
- The two RPC bodies each contain the availability line exactly once.
- `authenticated` can still EXECUTE both RPCs; `anon` cannot.
- `capability_customer_available` is false for the four withheld services and true for `FINANCIAL_STATEMENTS`.
- The journal holds exactly one row for the candidate, with the given `created_at`.

## 4. Outcomes and exit codes

| Outcome | Exit | Meaning | Changed anything? |
|---|---|---|---|
| `UNAPPLIED` (status) | 0 | Clean pre-state on the expected lineage | no |
| `APPLIED` | 0 | Committed and verified | yes — exactly the candidate + one journal row |
| `ALREADY_APPLIED` | 0 | Recorded once with the same `when`, every postcondition holds | no |
| `CONFLICT` | 10 | See below | no |
| `BUSY` | 12 | A lock was not granted within `lock_timeout` | no (rolled back) |
| `FAILED` | 13 | Any error before COMMIT, including a dropped connection | no (rolled back) |
| `UNCERTAIN` | 11 | The connection failed while COMMIT was in flight, or the post-commit verification disagreed | unknown — run `status` |
| refused | 2 | Candidate bytes/hash mismatch, bad arguments, URL not naming the project, or a `system_identifier` mismatch | no connection or no write |

`CONFLICT` covers each of these:
- the journal table is absent (wrong target);
- the lineage moved (the last entry is not 0025);
- the candidate is recorded more than once;
- it is recorded but the postconditions fail;
- its objects are present without a record (applied out of band);
- it is partially present;
- it is already recorded under a different `when`;
- `--when` is not after the last entry.

## 5. Recovery

- **BUSY or FAILED:** nothing changed. Read the message, run `status` (expect `UNAPPLIED`), remove the cause, and re-run `apply` with the same `--when`.
  - Typical causes: a long transaction holding the mandate table, or too short a timeout.
- **UNCERTAIN:** do not guess. Run `status`; it is read-only and authoritative, and resolves to exactly one of these:
  - `ALREADY_APPLIED` — committed; continue with step 4, using the recorded `created_at`;
  - `UNAPPLIED` — not committed; re-run `apply`.

  The transaction is atomic, so a partial state is impossible; `status` reports one as a CONFLICT if it ever appears.
- **CONFLICT:** stop. Do not apply by hand. Capture the `status` output and review it before any further action.
  - Out-of-band objects, a moved lineage or a duplicate row each need their own reviewed resolution.
- **After a successful apply:** the change is forward-only. Reversing it requires a separate, reviewed forward migration that:
  - restores the two previous RPC definitions;
  - drops the trigger and the three functions;
  - adds its own journal entry.

  The journal row is history and is never deleted.

## 6. Evidence (disposable PostgreSQL 16.14)
`DB_PROOF_MODULES_DIR=<dir with pg@8 + embedded-postgres> node scripts/db-proof/hostedApply.mjs` → **35/35**, three consecutive runs.

The disposable target replays every source migration before the candidate. Its `drizzle.__drizzle_migrations` is created with drizzle-orm's DDL and seeded with entries 0000–0025 exactly as drizzle records them. Every scenario runs on a fresh clone and drives the real CLI as a separate process.

- **Candidate verification:** exact bytes and hash. A one-byte change, CRLF, a BOM or truncation is refused before connecting.
- **Identity:** each of these is refused, with nothing changed:
  - a URL not naming the project;
  - a production ref in disposable mode;
  - a wrong `system_identifier`;
  - a missing `--when`;
  - the test hook outside disposable mode.
- **Apply:** `UNAPPLIED` → `APPLIED`, with one journal row (hash, `when`) and the exact `JOURNAL_ENTRY` printed.
  - Volatility is IMMUTABLE / STABLE / VOLATILE; the trigger is AFTER INSERT ROW; the ACLs are owner-only.
  - A service_role withheld-service GRANT is refused `PT422 SERVICE_NOT_AVAILABLE`, while `FINANCIAL_STATEMENTS` is accepted.
  - The only changes are the three functions, the two RPC bodies, the trigger and one journal row.
- **Repeat invocation:** `ALREADY_APPLIED`, byte-identical. A different `--when` is a `CONFLICT`.
- **Induced failures:** each leaves schema **and** journal byte-identical, and `status` afterwards reads `UNAPPLIED`:
  - failure after the SQL and the journal row, before COMMIT → `FAILED`;
  - lock contention → `BUSY`;
  - `statement_timeout` → `FAILED`;
  - backend terminated mid-transaction → `FAILED`.
- **Concurrent invocation:** 8 simultaneous processes → exactly 1 `APPLIED` and 7 `ALREADY_APPLIED`, with one journal row. Stable across three runs.
- **Conflicts:** each of these is `CONFLICT` from both `status` and `apply`, with nothing changed: applied out of band, partial, lineage moved, recorded twice, recorded but not applied, journal absent.

## 7. What this repository cannot establish (must be confirmed by the journal owner before production)

1. **The hosted journal's actual state.** The procedure assumes `drizzle.__drizzle_migrations` exists on the target and that its last row is 0025 (`621f55c3…`, `1790920391757`), as the repository journal records. Step 1 checks it read-only and refuses otherwise. It cannot be confirmed from here.
2. **How Lovable's tracked runner records entries.** The repository shows drizzle-kit 0.31.10 / drizzle-orm 0.45.2 and the default `drizzle.__drizzle_migrations`. It does not show Lovable's invocation: options, role, whether it wraps its own lock or timeouts, or how it chooses `when`. If Lovable's runner records differently, the row written here must be reconciled with Lovable before step 4.
3. **Coordination with Lovable's runner.** It takes neither lock. If it ran concurrently with an entry for the same candidate, it could re-execute the (idempotent) SQL and insert a second row, which this runner would then report as `CONFLICT` (recorded twice). The quiet period in §2 is therefore an operator requirement, not something the database enforces.
4. **The production server version and the owner of the existing RPCs.** The proof ran on PostgreSQL 16.14. `CREATE OR REPLACE TRIGGER` needs PostgreSQL ≥ 14. The connecting role must own `grant_engagement_capability` and `open_engagement_with_scope`.
